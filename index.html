    Build And Debugging

    On this pagePrerequisitesMake TargetsResource RebuildsHTTPS TestCI And Interactive TestsLogs And DiagnosticsDebugging Rules

    Prerequisites

    The documented Debian/Ubuntu dependencies include GCC/binutils tooling, NASM, GRUB tools, xorriso, make, and QEMU. The repository's build_gccbinutils.sh creates the cross-toolchain expected by the Makefile at $HOME/cross/bin/x86_64-elf-gcc and x86_64-elf-ld.

    Create a QEMU disk image before running the full storage workflow:

    fallocate -l 256M sata256.img

    Make Targets

    make build-x86_64
make run
make minimaSSL-slib
make clean

    build-x86_64 compiles enabled modules, kernel implementation files, minimaSSL crypto sources, resource packages, and embedded package objects. It links dist/x86_64/kernel.bin, copies it to the ISO input tree, and creates dist/x86_64/kernel.iso.

    run builds first, then starts QEMU with the ISO, serial console, USB keyboard, AHCI disk, RTL8139 networking, and audio devices.

    minimaSSL-slib builds the SDK library and copies the result to the distribution build. The install1 rule then copies it into src/resources/install1 before building the embedded package.

    clean removes kernel and distribution output, Minimal-OS-SDK/build, generated .run files, generated minimaSSL bundles, and package objects. It does not remove source resources or the disk image.

    Resource Rebuilds

    Resource directories are packaged into install1, install2, and install3:

    src/resources/install1 -> 0:/etc
src/resources/install2 -> 0:/programs
src/resources/install3 -> 0:/services

    Files added to install2/install3 are included as package prerequisites, so a changed program or service causes the corresponding embedded package to rebuild. Run make clean when removing a generated file should also remove its stale package object.

    HTTPS Test

    Run the focused TLS integration test:

    bash tools/debug/https_test.sh

    The script:

    1. builds the kernel;
    2. creates a temporary self-signed certificate;
    3. starts openssl s_server -tls1_3 on the host;
    4. starts QEMU with user-mode networking;
    5. sends n at the disk prompt;
    6. runs dhcp;
    7. runs wget https://10.0.2.2:8443/;
    8. checks for handshake and download completion.

    The test intentionally uses an IP address and defers certificate verification. It validates the TLS record/key schedule and HTTP exchange, not public CA trust.

    The crypto known-answer test is:

  tools/debug/mssl_tls_gcm_kat.c \

  -o /tmp/mssl_tls_gcm_kat

    CI And Interactive Tests

    make ci-test
make ci-interact

    ci_test.sh is intended for automated checks. ci_interact.sh drives the terminal over serial and waits for command-specific success patterns. When a pattern fails, inspect its serial output and the generated QEMU log.

    Logs And Diagnostics

    Useful output sources include:

    • serial terminal output for initialization, commands, services, and TLS;
    • tools/debug/https_test.log for the HTTPS test guest console;
    • tools/debug/https_server.log for OpenSSL trace output;
    • qemu.log for QEMU guest errors and interrupts.

    OpenSSL's bad record mac means it rejected an authenticated TLS record before it could decode the encrypted inner message. Compare it with the guest's TLS stage message; the server-side error is often the primary failure and the guest receive error is a follow-on alert/close.

    Debugging Rules

    Build the smallest focused test after a change. Preserve existing user changes in a dirty worktree. Avoid using generated logs as source-of-truth code. For kernel crashes, inspect process creation, allocator state, interrupt state, serial output, and the last subsystem initialization message in that order.

    Boot And Kernel

    On this pageBoot ChainStartup OrderMemoryProcesses And ThreadsScheduling And SMPSyscall BoundaryKernel Interfaces

    Boot Chain

    GRUB loads the Multiboot2 kernel from the ISO. The boot entry is split between src/impl/boot/main.asm and src/impl/boot/main64.asm:

    1. Save the Multiboot information pointer.
    2. Verify the Multiboot signature, CPUID, and x86_64 long-mode support.
    3. Build initial PML4, PDPT, and page-directory tables.
    4. Enable PAE, long mode, NX, and paging.
    5. Load the 64-bit GDT and jump to long_mode_start.
    6. Pass the Multiboot information address to kernel_main().

    The initial low-memory map uses 2 MiB pages. PML4 slot 511 is reserved for a high MMIO address range. Later device mappings are made by src/impl/kernel/mmio.c. The Multiboot memory-map tag is parsed by multiboot2parse.c to determine the available RAM reported to the allocator and system information commands.

    The GRUB menu provides three entries: Minimal-OS for normal startup, Minimal-OS Memory Tester x64 for a standalone pattern test of free PMM pages, and Minimal-OS (No Disk) to boot without probing or mounting storage. The memory test reserves only free PMM pages and halts after reporting PASS or FAIL.

    Startup Order

    kernel_main() in src/impl/kernel/main.c performs the high-level startup:

    • serial output, BSP/SMP state, GDT, and command registration;
    • memory and startup routines;
    • PCI enumeration;
    • USB and graphics driver-manager registration;
    • RTL8139 network registration, Ethernet/IP/UDP/TCP setup, and network syscall state;
    • time and random seeding;
    • audio and AHCI storage-driver registration;
    • AP startup, interrupts, kernel background processes, and the terminal.

    The terminal owns the disk interaction. In normal mode it probes and mounts the disk and starts services; no-disk mode skips that path and still starts the terminal and keyboard tasks.

    Memory

    The physical memory manager (src/impl/pmm.c) allocates 4 KiB pages. The heap allocator (src/impl/kernel/allocator.c) provides variable-size allocations for kernel structures, file buffers, process objects, and driver state.

    Use page allocation for DMA-aligned or page-owned memory. Use alloc() or alloc_unzeroed() for ordinary objects. Large structures such as directory descriptors are deliberately heap allocated because kernel stacks are small.

    Processes And Threads

    Kernel processes are created with createProcess(name, entry). A process entry must either loop, call sleep(), or terminate through process_exit()/kill(); returning from a raw kernel entry is not a normal completion mechanism.

    User .run programs are loaded as user processes. The loader creates an image, user stack, page mappings, and argument block, then enters ring 3 through the process trampoline. See user programs.

    Threads are lightweight wrappers around kernel processes. thread_join() polls for process termination while yielding through sleep().

    Scheduling And SMP

    Each online CPU owns a run queue with three levels:

    • interactive: terminal input and short blocking work;
    • normal: ordinary processes;
    • background: CPU-heavy or lower-priority work.

    A process that consumes its quantum is demoted. A process that blocks is promoted on wake. Periodic boosting prevents starvation, and periodic rebalancing moves queued processes between CPUs when the load difference is large enough.

    Run-queue locks are SMP-safe spinlocks. cli only disables interrupts on the current CPU; it is not a replacement for an atomic lock shared by CPUs.

    process_t contains fields consumed by context-switch assembly. Fields before the documented ABI boundary must not move without updating the assembly and verification code.

    Syscall Boundary

    User code invokes int 0x80. The syscall ISR saves registers into the packed syscall_regs_t layout, and syscall_dispatch() validates the requested operation and user pointers before calling a subsystem implementation.

    The user privilege table is separate from the syscall number table. For example, a user program may use TCP and filesystem calls, while DHCP remains a privileged operation because it changes the machine-wide network configuration. See user SDK syscalls for the complete user-facing API.

    Kernel Interfaces

    Public kernel contracts live in src/intf:

    • x86_64/proc.h and x86_64/scheduler.h define process/scheduler state.
    • x86_64/allocator.h and x86_64/pmm.h define memory allocation.
    • x86_64/minimafs.h defines filesystem objects and operations.
    • x86_64/syscall.h defines the syscall ABI structures and constants.
    • subsystem manager headers define driver registration and lifecycle methods.

    Implementations can grow internal structures, but shared headers and assembly offset contracts must remain synchronized.

    Hardware And Drivers

    On this pageDriver Manager PatternPCI And MMIOGraphicsUSBAudioStorageAdding A Driver

    Driver Manager Pattern

    Hardware support is registered during kernel startup through manager APIs. A manager selects an available driver, initializes it, and exposes a stable subsystem interface to the rest of the kernel. This keeps device-specific code out of terminal commands and protocol implementations.

    Relevant interfaces are in src/intf/x86_64 and implementations are in src/modules:

    • network_manager.h / network drivers;
    • gpu_manager.h / framebuffer drivers;
    • usb_manager.h / host-controller and device drivers;
    • audio manager interfaces;
    • storage manager and AHCI interfaces.

    A missing device is normally a supported degraded state. Graphics can continue headless, USB can fall back to PS/2, and audio can report that no compatible controller exists.

    PCI And MMIO

    PCI enumeration discovers devices by bus, device, and function. Driver code reads vendor/device IDs and maps BARs through the kernel MMIO allocator rather than using arbitrary virtual addresses.

    The MMIO subsystem reserves a high virtual range, creates page-table entries, and maps device registers or framebuffer memory. Device mappings must remain page aligned and should use the mapping helpers rather than direct identity assumptions.

    Graphics

    The display itself still comes from the linear framebuffer the bootloader set up (VBE on BIOS, GOP on UEFI); the Bochs/VBE driver can also set modes on QEMU's 1234:1111 device. Framebuffers are mapped write-combining (PAT entry 1), which makes pixel writes to a real graphics card much faster.

    On top of that, gpucore.c turns each display-class PCI device into a GPU adapter with video memory: total VRAM, the PCI BAR that is the CPU's window onto it, where the visible framebuffer sits in VRAM, and a VRAM allocator for the rest. Drivers:

    DriverDevicesWhat it knows
    gpu_nvidia.cNVIDIA, tuned for GTX 10 (Pascal) and RTX 20 / GTX 16 (Turing)chip and board name, VRAM size from the memory controller, BAR1 window, temperature
    gpu_bochs.cQEMU/Bochs standard VGAVRAM size, page flipping
    gpu_generic.ceverything elsethe framebuffer's BAR as VRAM window

    Drawing commands go through the FGPU command processor (SYS_GPU, fgpu.c), whose current backend renders 3D on the CPU. See GPU and 3D.

    USB

    UHCI and OHCI (USB 1.1) and xHCI (USB 3, every recent PC) controllers are driven. Directly attached HID boot keyboards and mice work on all three; hubs, EHCI, and USB storage are not supported yet. On xHCI the kernel takes the controller over from the firmware (legacy hand-off) and polls its event ring from the timer interrupt.

    PS/2 keyboards work too: the 8042 controller is initialised at boot and its scan codes are converted to the same HID reports, so layouts and key repeat behave the same as with USB.

    User programs use SYS_USB wrappers for initialization, polling, keyboard presence, key translation, and keyboard metadata.

    Audio

    Audio drivers are registered through the audio manager. The AC'97 path searches for a compatible controller, configures the device, and provides a mix/update callback. The kernel audio process updates playback independently of the terminal.

    If no compatible audio controller is present, initialization reports that state and the rest of the system continues.

    Storage

    Disks are block devices (blockdev.c): every SATA disk on every AHCI controller (sata0, sata1, ...) and every NVMe namespace (nvme0, ...). MBR and GPT partitions become child devices (sata0p1, nvme0p2). MinimaFS works on any block device, so a volume can be a whole disk (the original layout) or a partition. See Storage and packages.

    The filesystem uses a DMA bounce buffer for block I/O; the NVMe driver builds PRP lists and is polled.

    Adding A Driver

    A new driver normally needs:

    1. a hardware-facing interface structure and callbacks;
    2. a manager registration call during kernel_main();
    3. PCI/device detection and resource mapping;
    4. an implementation under src/modules or the relevant subsystem;
    5. a fallback behavior when the device is absent;
    6. build configuration in config.mk if the module is optional.

    Keep interrupt handlers short, protect shared state with the appropriate local interrupt and SMP locking rules, and expose only subsystem-level operations to commands and user syscalls.

    GPU and 3D

    Adapters and video memory

    gpu_core_init() (after the display driver is up) gives every display-class PCI device a gpu_adapter_t (src/intf/x86_64/gpucore.h):

    • vram_size – total video memory,
    • aperture_* – the PCI BAR through which the CPU sees VRAM, mapped write-combining,
    • scanout_* – where the framebuffer the screen shows sits in VRAM,
    • heap_start/heap_end – the rest of the window, handed out by gpu_vram_alloc(); it is only enabled after a write/read-back test.

    gpu in the terminal prints all of this.

    NVIDIA (GTX 10 "Pascal", RTX 20 / GTX 16 "Turing")

    gpu_nvidia.c reads the chip from PMC_BOOT_0, the board name from the PCI device id (GT 1030, GTX 1050/1050 Ti/1060/1070/1080, RTX 2060/2070/ 2080 and their variants, GTX 1650/1660), the VRAM size from the memory controller (register 0x100CE0, as nouveau does for Pascal through Turing) and the core temperature. BAR1 is the VRAM window; it is only used for allocations while BAR1 is in physical mode, which is how the firmware leaves it.

    The display mode is the one the firmware set (GOP/VBE). FGPU work is rendered on the CPU into VRAM; see NVIDIA cards and hardware rendering for what running it on the card itself takes.

    QEMU / Bochs

    gpu_bochs.c reads the VRAM size and can page flip (show any line of VRAM). Because VRAM is ordinary host memory there, the kernel's screen back buffer is moved into VRAM as well. Give QEMU more VRAM with -vga none -device VGA,vgamem_mb=64 (make run does).

    FGPU command processor

    SYS_GPU (40) is the GPU interface for programs (fgpu_abi.h, shared word for word with the SDK). A process creates *surfaces* (color XRGB8888, depth float32), *buffers* (vertices, indices) and *shader programs*, records a command buffer (bind target, viewport, clear, state, program or shader, constants, vertex layout, textures, draw) and submits it; then presents a color surface to the screen (copy, or page flip when the surface is in VRAM and the adapter can flip) or into a window. Everything is freed when the process exits.

    ABI version 2 added shader programs (CREATE_PROGRAM, DESTROY_PROGRAM), texture uploads (WRITE_SURFACE) and the commands SET_SHADER, SET_CONSTANTS, SET_VERTEX_LAYOUT and BIND_TEXTURE, plus the FGPU_STATE_BLEND state. The kernel still accepts version-1 requests, so older programs keep working.

    CPU backend

    fgpu_raster.c runs the pipeline: vertex stage, near-plane clipping, perspective-correct rasterization with the top-left rule, depth test, back/front face culling, wireframe, fragment stage and alpha blending. The built-in programs (vertex color, Gouraud, per-pixel Phong with Blinn-Phong highlights) are hard-wired C code.

    Shader machine

    Shaders are FGPU bytecode (described at the end of fgpu_abi.h): vec4 registers in a few files (temporaries, inputs, outputs, uniforms, constants, fragment specials), five-word instructions with swizzles, write masks and negate/abs modifiers, and about forty opcodes (arithmetic, dot products, pow/exp2/log2/sin/cos, mix/clamp/ smoothstep, comparisons and select, texture sampling, discard, jumps). The SDK's FGSL compiler (fglsl.h) produces it from GLSL-style source.

    fgpu_shader.c:

    • fgpu_program_check validates a program once, on the kernel's own copy: every opcode, register index, write mask, texture unit and section bound. Jumps may only go forward, so a program runs at most its instruction count (2048 per stage) and cannot hang the kernel. Rejected programs are logged to serial (fgpu: shader program rejected: ...).
    • The interpreter runs 8 invocations at once, like a GPU warp: registers are stored per component as 8-lane rows and the lane loops use SSE (GCC vector extensions). Branches are handled per lane with a "resume at" instruction: lanes that jump wait until execution reaches their target, so divergent if/else runs correctly. Temporaries are zeroed for every draw, so a shader never sees other data.
    • The rasterizer queues covered pixels and shades them 8 at a time, and runs each triangle's three vertices as one batch. A shader that can discard writes depth after the fragment stage instead of before it.

    make test-host runs the compiler, checker, machine and rasterizer end to end (tests/host/fgsl_tests.c), including a check that a shader version of a built-in program gives the same pixels.

    Speed: the fglcube scene at 640 × 480 on one 2.8 GHz core takes about 11 ms per frame with the built-in Phong program and about 42 ms with fglcube --shader (a 60-instruction fragment shader over about 180,000 pixels).

    FarcadeGL

    The SDK's farcadegl.h wraps all of this in an OpenGL/Vulkan-like API with GLSL-style shaders. Guides: farcadegl.md (API) and fgsl.md (shading language), also in Minimal-OS-SDK/docs/. fglcube (terminal, full screen; fglcube --shader for the shader version) and MOSdesk's *Cube* app (press S) are examples.

    NVIDIA cards and hardware rendering

    Today FGPU renders on the CPU on every adapter. Running it on the graphics card's own engines is the next step, and on NVIDIA cards it is possible with open code. This section explains what stands in the way and how open drivers get around it.

    What has to be signed

    Since the GTX 900 series, an NVIDIA GPU only lets firmware signed by NVIDIA run on its internal microcontrollers ("falcons", and on RTX 20 and later the GSP, a RISC-V core). That firmware sets up the graphics engine's context-switching units (FECS/GPCCS), power management and memory protection; without it the graphics engine does not run.

    What does *not* have to be signed:

    • the command streams (pushbuffers) a driver sends to a channel: "set this register of the 3D class, draw these vertices";
    • the shader programs the shader cores (SMs) execute.

    Both are written by the driver. So an open driver needs NVIDIA's firmware files, but nothing it produces itself has to be signed.

    How open drivers do it

    nouveau (Linux) and NVIDIA's own open kernel modules load NVIDIA's signed firmware files, which NVIDIA publishes for redistribution in the linux-firmware repository (nvidia/gp10x/..., nvidia/tu10x/..., under NVIDIA's firmware licence, LICENCE.nvidia). Minimal-OS can do the same: ship those files unchanged on the system volume and load them at boot. Then:

    GTX 10 (Pascal)RTX 20 / GTX 16 (Turing)
    FirmwareACR + graphics (FECS/GPCCS) + SEC2 images from linux-firmware, booted through the secure-boot falcon as nouveau doesThe GSP firmware (gsp-*.bin) plus its boot loader; GSP then sets up most of the chip itself
    Driver talks toRegisters directlyGSP through a message queue (RPC), as nouveau's GSP mode and NVIDIA's open kernel modules do
    Clock speedsStays at boot clocks: NVIDIA never released the PMU firmware needed to raise them, so 3D runs much slower than the card's real speedFull speed (GSP manages clocks)
    CommandsChannels with a GPFIFO of pushbuffers; 3D class PASCAL_A/PASCAL_BSame, 3D class TURING_A

    The class methods (register meanings) are published by NVIDIA in open-gpu-doc. The shader instruction set (SASS) is not officially documented, but Mesa's open compilers (the nouveau codegen and NAK, used by the NVK Vulkan driver) generate it, and envytools documents much of it.

    The plan for Minimal-OS

    1. Firmware loading: read the linux-firmware files from 0:/firmware/nvidia/, check them, and boot GSP on Turing (simpler and full speed) or ACR on Pascal.
    2. Channels: allocate a channel, a GPFIFO and pushbuffers in VRAM, and submit a "clear the screen" through the 3D class to prove the path.
    3. An FGPU hardware backend: translate FGPU command buffers to pushbuffers (surfaces → render targets, DRAW → vertex buffer setup and draw methods) and FGPU shader bytecode to SASS. The bytecode was designed for this: straight-line code with forward jumps, vec4 registers and a small instruction set map well onto a GPU compiler.
    4. Programs do not change: FarcadeGL and FGSL stay the same, and syscall_gpu_info_t.backend reports the hardware backend.

    This needs testing on real cards (QEMU cannot emulate an NVIDIA GPU); steps 1-2 are the first milestone.

    The shader IR

    GPU shader cores run 32 threads in step, each on scalar 32-bit registers, so fgpu_ir.c turns each vec4 instruction into scalar operations that correspond one to one to Turing instructions (FFMA, FMNMX, MUFU.RSQ, FSET.BF, FSEL, TEX, IPA, ...):

    • the edge cases FGPU defines (x / 0 = 0, sqrt/rsq of x <= 0, log2(x <= 0) = -126, pow of x <= 0) become explicit selects, so GPU and CPU agree;
    • atan2, smoothstep, mod and sign become short instruction sequences (the same polynomial as the CPU backend);
    • jumps are if-converted: each thread keeps the instruction it resumes at, as the CPU interpreter does per lane, and writes inside a skipped range become selects. The result has no branches at all; turning long skipped ranges back into real branches (BRA with BSSY/BSYNC) is a later optimization.

    MinimaFS Model

    MinimaFS stores a directory tree in 4 KiB blocks on an AHCI-backed disk. Mounted drives use paths such as 0:/, 1:/, and 0:/programs. Metadata records file type, format, size, timestamps, runnable state, and block layout. Directory descriptors contain entries and storage descriptors track the volume root, block counts, and free space.

    The filesystem API is declared in src/intf/x86_64/minimafs.h. Commands should use resolved MinimaFS paths and the API rather than constructing raw disk structures.

    Disks, partitions and drives

    disks                                  list disks, partitions, filesystems
part sata1                             show sata1's partition table
part sata1 init gpt --yes              new empty GPT (or mbr)
part sata1 add 500G minimafs data      add a partition (sizes: 512M, 20G, 2T, rest)
part sata1 del 2                       delete partition 2
format sata1p1 1 data                  MinimaFS on sata1p1, mounted as 1:
mount sata1p2 2                        mount an existing volume as 2:
umount 2
drives                                 mounted drives and their usage
format                                 (no arguments) the boot volume as 0:, with system files

    At boot the system volume is mounted as 0: (the one named by root=<partition GUID or device> on the kernel command line, else the first MinimaFS volume found), and every other MinimaFS volume as 1:, 2:, ... in disk order.

    A MinimaFS volume can hold up to 2^32 - 2 blocks of 4 KiB, just under 16 TiB. Free space is tracked as a list of used extents rebuilt at mount time, so memory use does not grow with the volume size. MBR can address disks up to 2 TiB; use GPT beyond that (the default).

    MinimaFS partitions use GPT type 4D696E69-6D61-4653-B0A7-4D4F534D4653 or MBR type 0x7F.

    To make a disk boot by itself, use install (see Installing).

    Embedded Install Packages

    The root Makefile packages these directories as MPKG0001 archives:

    SourceDestination after format
    src/resources/install10:/etc
    src/resources/install20:/programs
    src/resources/install30:/services

    The archives are converted to ELF binary objects with objcopy and linked into the kernel. This is intentional: a newly formatted disk has no files from which the format command could load an installer.

    install1 receives the generated minimaSSL.slib. A service file added to install3 is therefore present at 0:/services before service discovery runs.

    MPKG Format

    The host builder is tools/mkpkg/mkpkg.py. It writes:

    • an 8-byte MPKG0001 magic;
    • a version and entry count;
    • fixed-size entry records with names, flags, compression method, sizes, and payload offsets;
    • stored or LZSS-compressed payload data.

    Directory entries have no payload. File entries use either MPKG_METHOD_STORE or MPKG_METHOD_LZSS. The kernel validates names, table bounds, payload ranges, and decompression output before writing an entry.

    Use the command interface to work with packages already on disk:

    pkg zip 0:/source store
pkg unzip 0:/archive.mpkg 0:/target
pkginfo 0:/archive.mpkg
installpkg 0:/archive.mpkg 0:/target

    User programs use mos_pkg_zip(), mos_pkg_unzip(), and mos_pkg_info() over SYS_PKG.

    File Operations

    Kernel code can create, open, read, write, list, delete, and remove files through MinimaFS. User code uses the corresponding SDK wrappers:

    • mos_open() and mos_close() manage existing files;
    • mos_read() and mos_fwrite() transfer data;
    • mos_seek(), mos_tell(), mos_size(), and mos_feof() inspect position;
    • mos_create() creates an empty file before opening it writable;
    • mos_listdir(), mos_exists(), and mos_is_dir() inspect paths;
    • mos_get_metadata() returns stable user-facing metadata.

    Filesystem paths are strings, not user-space integer descriptors in the public SDK. Open file handles are kernel-owned values returned by SYS_OPEN and must be closed.

    Safety Rules

    Package extraction must reject absolute paths and .. traversal. Validate sizes before allocating or reading payloads. Use heap memory for directory structures and large file buffers instead of kernel stacks. When adding a new format or package feature, keep the host encoder and kernel decoder constants synchronized.

    Networking

    On this pageStack LayersInitializationDHCPDNSTCPUDPTLS And Wget

    Stack Layers

    The kernel network path is:

    RTL8139 -> Ethernet -> IPv4/ARP -> UDP/TCP -> syscall handles

    network_manager selects the NIC driver. Ethernet frames are passed to IPv4, which dispatches UDP and TCP payloads. ARP resolves next-hop IPv4 addresses to MAC addresses. The protocol implementations live in src/impl/net.

    The stack uses host-order IPv4 addresses in its internal and user syscall APIs. Only wire headers use network byte order.

    Initialization

    kernel_main() registers the RTL8139 driver and initializes Ethernet, IP, UDP, TCP, and net_syscall. The NIC must be initialized before protocol traffic can be sent. network_manager_poll() pumps received frames and is called from blocking protocol operations and user polling wrappers.

    The stack has bounded connection, listener, handle, and receive-queue tables. The SYS_ERR_BUSY result means another caller currently owns a non-reentrant network operation; retry it rather than treating it as a permanent failure.

    DHCP

    The terminal dhcp command sends a DISCOVER, waits for an OFFER, sends a REQUEST, and waits for an ACK. It configures:

    • guest IPv4 address;
    • netmask;
    • gateway;
    • DNS server.

    DHCP is intentionally an operator action. A user .run program calling mos_net_dhcp() receives SYS_ERR_PERM because changing the lease changes the machine-wide interface configuration.

    DNS

    dns_resolve() sends a UDP A-record query to the configured DNS server. The resolver registers a temporary UDP handler, pumps the NIC while waiting, and removes the handler when the query completes or times out.

    The terminal wget command resolves a hostname when the URL does not contain a numeric address. DNS failures are reported separately from TCP and TLS failures.

    TCP

    TCP supports active connections, listeners, accept queues, retransmission, ACKs, receive buffers, and bounded send windows. User programs receive integer handles rather than raw tcp_conn_t* pointers. Handles are owned by the creating process and are closed when the owner dies.

    Client pattern:

    long h = mos_tcp_connect(ip, 80, 5000);
if (h > 0) {
    mos_tcp_send(h, request, request_len);
    mos_net_poll();
    mos_tcp_recv(h, buffer, sizeof buffer);
    mos_tcp_close(h);
}

    Server pattern:

    long listener = mos_tcp_listen(8080, 4);
long client = mos_tcp_accept(listener, &peer_ip, &peer_port);

    mos_tcp_accept() is non-blocking. It returns zero when the backlog is empty and SYS_ERR_AGAIN is normalized to zero by the SDK wrapper. A server should sleep briefly between attempts. mos_tcp_handoff() transfers an accepted connection to a child process.

    UDP

    A user program binds a UDP handle, receives queued datagrams, and sends to a host-order destination address. Datagrams larger than the destination buffer are truncated and the remainder is discarded.

    Broadcast uses SYSCALL_NET_IP_BROADCAST. The QEMU user-mode network backend does not forward LAN broadcasts beyond the guest, so broadcast discovery needs a tap or bridged network configuration.

    TLS And Wget

    The kernel wget command performs a TLS 1.3 client handshake over TCP. The current tested cipher path is TLS_AES_128_GCM_SHA256:

    1. create a ClientHello with X25519 key share;
    2. parse ServerHello and derive handshake traffic secrets;
    3. authenticate encrypted handshake records;
    4. verify the server Finished message;
    5. derive application traffic secrets;
    6. send the HTTP request in an encrypted application record;
    7. decrypt the HTTP response.

    The TLS client defers certificate verification. It is suitable for the current controlled integration test but should not be treated as a complete web PKI client. tools/debug/https_test.sh runs an OpenSSL TLS 1.3 server and verifies this path end to end.

    Discovery And Registration

    Services are filesystem definitions, not C registration calls. After the boot disk is mounted, terminal_program_entry() calls service_manager_init(). The manager scans 0:/services, accepts files whose names end in .service, parses them, and creates a monitor process for each valid entry.

    A service is registered only when it has at least one [STARTUP] action: exec or script. The terminal command services lists entries that parsed and registered successfully.

    Services are optional modules. In particular, the window manager is not required to boot or use the built-in terminal. Installing its executable alone does not start it; automatic startup is enabled by placing its mosWM.service definition in 0:/services. If the definition or executable is missing, service discovery skips the entry and the OS continues without a window manager. Remove the service definition and reboot to disable automatic startup.

    [GENERAL]
name="mosWM"
desc="Optional graphical window manager"
exit=None

[STARTUP]
exec="0:/programs/mosWM/mosWM.run"

    File Format

    [GENERAL]
name="Example Service"
desc="Runs an example"
exit=Restart
exitscript="run 0:/programs/recovery.run"

[STARTUP]
exec="0:/programs/example.run"

    Supported general keys:

    • name: display name; defaults to the filename;
    • desc: text shown by services;
    • exit: None, Restart, or Script;
    • exitscript: command used by Script after a monitored process exits.

    Supported startup keys:

    • exec: direct .run path, run <path>, or an arbitrary terminal command;
    • script: run <path> for a launchable .run, or another command string.

    Values may be quoted. // starts a comment outside quotes.

    Startup Forms

    A directly monitored executable uses a path:

    [STARTUP]
exec="0:/programs/worker.run"

    The equivalent command form is also recognized:

    [STARTUP]
exec="run 0:/programs/worker.run"

    An arbitrary command can be run once:

    [STARTUP]
exec="echo service started"

    Command-style entries call the terminal command dispatcher and do not expose a process ID to the service monitor. exit=Restart and exit=Script therefore cannot supervise their completion. Use a .run path when restart or exit handling is required.

    Supervision

    For a direct .run launch, the manager:

    1. normalizes the path to a 0:/... path;
    2. launches the bundle as a process;
    3. waits for its process ID;
    4. applies the exit policy.

    None stops after exit. Restart waits briefly and starts again. Script executes exitscript once and then stops.

    A failed launch is logged on serial and does not create a usable monitored service. A malformed file, missing startup action, or unsupported startup configuration is skipped.

    Packaging A Service

    Place the definition in src/resources/install3:

    src/resources/install3/example.service

    make build-x86_64 packages install3 and embeds it in the kernel. Running format extracts it to 0:/services before service discovery. A referenced .run program should be placed in src/resources/install2, which becomes 0:/programs.

    The complete install mapping is:

    install1 -> 0:/etc
install2 -> 0:/programs
install3 -> 0:/services

    Troubleshooting

    Use services after mounting to inspect registrations. Use the serial console to distinguish these cases:

    • no services directory: install3 was empty or format did not run;
    • parse failure: the file syntax or section/key names are invalid;
    • no startup action: add exactly one exec or script key;
    • failed to start: the referenced .run path is missing or invalid;
    • repeated starts: the service has exit=Restart and exits normally.

    Program Model

    The SDK produces self-contained x86_64 PIE programs with no dynamic linker. The kernel loads these programs as user processes and enters them in ring 3. The current process model still shares the kernel PML4, so the syscall ABI is a capability boundary but not yet a fully isolated address-space boundary.

    Build a program with:

    Minimal-OS-SDK/build.sh Minimal-OS-SDK/examples/hello.c

    The output is a .run bundle. Import it into MinimaFS, normally under 0:/programs, and run it with:

    run 0:/programs/hello.run

    .run Bundles

    A .run contains a MINIRUN1 header, an entry table, main.elf, and optional resource files. The kernel extracts main.elf, loads its PT_LOAD segments, and applies supported R_X86_64_RELATIVE relocations.

    The loader validates:

    • ELF64 little-endian format;
    • x86_64 machine type;
    • ET_EXEC or ET_DYN image type;
    • program-header bounds;
    • segment file-size and memory-size relationships;
    • maximum file and image sizes.

    The SDK linker script keeps the image base-relative. External symbols are not available because there is no dynamic linker or libc at runtime.

    Arguments And Exit

    The first argument is the program path. Extra arguments follow it. The SDK runtime calls mos_exit(code) to terminate, passing the low 8 bits of code back to the kernel. Returning from main() passes its return value as the exit code. A user-mode CPU fault terminates the program with code 0xff and prints a crash reason, such as Program crashed! Code 0xff: Memory page fault.

    Use mos_register_cleanup() when a user program needs a chance to save state before Ctrl+C or a requested termination. The kernel gives the cleanup callback a bounded period before force termination.

    Heap allocations made through the SDK are tracked by their owning process. Explicitly free allocations when practical; any remaining allocations are reclaimed when the process exits or is terminated. Invalid or cross-process heap pointers are rejected by the heap syscalls. This is exit-time reclamation, not tracing garbage collection, so it does not collect unreachable objects while a process is still running.

    SDK Runtime

    The SDK provides freestanding headers and small wrappers rather than a normal libc. Common facilities include:

    • stdio.h: terminal output helpers;
    • stdlib.h: heap, random bytes, and integer conversion;
    • string.h: memory and string operations;
    • minimalos.h: core syscalls and package/file wrappers;
    • net.h: TCP, UDP, DNS, and polling;
    • graphics.h: graphics operations;
    • x86_64/user_sysinfo.h: system and memory statistics.

    The runtime is built with freestanding flags, no stack protector, no exceptions, no RTTI, and no dynamic linker. See SDK syscalls for API contracts and examples.

    .slib Bundles

    The SDK can build a shared-library bundle:

    Minimal-OS-SDK/build.sh --slib Minimal-OS-SDK/libraries/minimaSSL

    A .slib contains:

    • library.elf;
    • exports.txt with global symbols;
    • public headers under include/.

    The bundle format is MINISLIB1. It is package metadata for a future/runtime loader; Minimal-OS does not currently dynamically load .slib code. The current kernel TLS path statically links the freestanding minimaSSL implementation and also installs the .slib at 0:/etc/minimaSSL.slib for distribution.

    Writing A Program

    A minimal program should include the SDK headers, perform work, and terminate:

    #include "minimalos.h"
#include "stdio.h"

int main(int argc, char** argv) {
    (void)argc;
    (void)argv;
    puts("hello from user space");
    mos_exit(0);
    return 0;
}

    For long-running programs, sleep or poll rather than busy-looping. Network programs must call mos_net_poll() or use the deadline helpers so the kernel network stack can process incoming frames.

    Security And Capability Notes

    User programs can access only syscall operations permitted by the kernel's privilege table. DHCP is privileged. File, network, process, graphics, USB, heap, random, and package operations have individual validation paths.

    Do not pass kernel pointers through the ABI. Use the public request structures, user buffers, and returned handles. Always close file, TCP, UDP, and TLS handles.

    Calling Convention

    The SDK invokes the kernel with int 0x80:

    • rax: syscall number;
    • rdi, rsi, rdx: the first three arguments;
    • rax on return: result value.

    Pointer arguments must point to user-readable or user-writable memory as required by the operation. Request-structure syscalls pass a pointer in rdi. Do not pass kernel-internal structures or pointers through the ABI.

    Most wrappers return long. Success is usually non-negative; failures are negative values represented in the unsigned syscall type. Use the constants rather than comparing against a raw magic number.

    Heap And Randomness

    stdlib.h maps the standard allocation names to SYS_HEAP:

    char* data = malloc(4096);
if (!data) mos_exit(1);
/* use data */
free(data);

    Available operations are malloc, calloc, realloc, and free. Allocation failure becomes NULL. realloc() leaves the original allocation valid when it fails. mos_random_bytes() uses the kernel random source and returns a byte count; mos_random_u64() is a convenience wrapper.

    The current implementation backs user heap allocations with the kernel heap. That is an implementation detail and should not be used to infer unrestricted kernel access.

    Graphics

    SYS_GRAPHICS receives a syscall_graphics_request_t. The SDK headers provide wrappers for:

    • width and height queries;
    • bounded opaque or alpha surface blits into a kernel back buffer;
    • dirty-rectangle presentation and packed framebuffer information;
    • clear, pixel, line, rectangle, circle, triangle, and ellipse drawing;
    • text output and text measurement;
    • resolution changes;
    • terminal clear.

    Screen ownership uses mos_graphics_acquire(), mos_graphics_release(), and mos_graphics_owner(). A process must acquire the screen before drawing; only the owner may perform drawing operations. Acquire fails with SYS_ERR_PERM if another process owns the screen. Release redraws the terminal, and ownership is reported as a PID or SYS_ERR_NOTFOUND when no process owns it.

    mos_graphics_blit_surface() accepts an ARGB8888 source surface, byte pitch, source rectangle, destination origin, and either SYS_GRAPHICS_BLIT_OPAQUE or SYS_GRAPHICS_BLIT_ALPHA. The complete source range must belong to one live user-heap allocation. The kernel caps each source at 64 MiB and stages it before compositing. mos_graphics_present(x, y, width, height) copies a clipped dirty rectangle to the framebuffer and is owner-only. mos_graphics_info() fills a versioned syscall_graphics_info_t with dimensions, pitch, framebuffer channel layout, and the back-buffer format SYS_GRAPHICS_PIXEL_FORMAT_ARGB8888.

    Use graphics.h for the shorter API or x86_64/user_graphics.h for raw-style wrappers. Coordinates and sizes are passed in the request's integer argument array; strings and output dimensions use validated pointers.

    Device Managers And USB

    SYS_MANAGER selects a manager and operation. The SDK exposes manager IDs for GPU, audio, storage, and USB, with operations such as init, update, start, has-data, and sample-rate configuration.

    SYS_USB supports:

    • mos_usb_init();
    • mos_usb_poll();
    • keyboard presence checks;
    • scancode/modifier to ASCII translation;
    • pressed-key queries;
    • keyboard device metadata.

    SYS_MOUSE provides mouse initialization, polling, presence, and accumulated relative state (dx, dy, wheel, and button bitmask).

    SYS_INPUT_READ consumes key down/up, mouse motion/button, and wheel events from a 256-entry bounded queue. Only the graphics screen owner may read it. mos_input_read(events, capacity, timeout_ms, dropped_count) caps each read at 256 events and the blocking timeout at 5 seconds; a zero timeout polls once. When no graphics owner is active, the queue ignores hardware input so the terminal remains the input consumer. Overflow drops the newest event and increments the optional dropped-event counter.

    Packages

    SYS_PKG uses a syscall_pkg_request_t structure:

    uint32_t installed = 0, failed = 0;
long rc = mos_pkg_unzip("0:/packages/app.mpkg", "0:/programs",
                        &installed, &failed);

    Wrappers:

    • mos_pkg_unzip(archive, target, installed, failed);
    • mos_pkg_zip(source, algorithm, output, output_size);
    • mos_pkg_info(archive, entry_count).

    Algorithms are "lzss" or "store"; NULL selects the default. Package extraction validates archive names and reports individual entry failures separately from whole-archive failures.

    System Information And Processes

    user_sysinfo.h exposes statistics through SYS_SYSINFO:

    • CPU usage;
    • total, used, and free RAM;
    • uptime;
    • process and online-core counts;
    • heap used/free bytes;
    • physical page used/free counts;
    • per-core usage using SYS_SYSINFO_CORE_USAGE_BASE + core_id.

    mos_pslist() writes process records containing PID, name, state, privilege, CPU assignment, and scheduler level. Its buffer belongs to the caller.

    Networking

    SYS_NET uses a syscall_net_request_t pointer. IPv4 addresses and ports are host-order values. net.h provides wrappers for status, resolve, polling, TCP, UDP, and the experimental TLS handle namespace.

    Status And DNS

    syscall_net_status_t status;
mos_net_status(&status);
uint32_t ip;
mos_net_resolve("example.com", &ip, 5000);

    mos_net_dhcp() is privileged and returns SYS_ERR_PERM from ordinary user programs. Run dhcp in the terminal first.

    TCP Client

    long conn = mos_tcp_connect(ip, 80, 5000);
if (conn > 0) {
    mos_tcp_send(conn, request, request_len);
    while (mos_net_poll() == 0) mos_sleep(10);
    long got = mos_tcp_recv(conn, buffer, sizeof buffer);
    mos_tcp_close(conn);
}

    mos_tcp_recv() returns zero when no data is ready and a negative error when the handle is invalid or the peer is closed. Deadline helpers in net.h pump polling and sleep between attempts.

    TCP Server And Ownership

    mos_tcp_listen() creates a listener handle. mos_tcp_accept() is non-blocking and returns zero when no client is queued. After starting a child, mos_tcp_handoff(connection, child_pid) transfers ownership so the child can use the accepted handle. The handle number is normally passed as an argument.

    UDP

    mos_udp_bind() creates a handle. mos_udp_recv() returns a datagram and fills source address/port outputs. mos_udp_send() sends to a host-order destination; SYSCALL_NET_IP_BROADCAST is the broadcast address.

    TLS Handles

    The ABI defines separate TLS connect, accept, state, send, receive, and close operations. TLS handshakes advance when SYS_NET_TLS_STATE or other TLS calls pump the session. SYS_ERR_AGAIN means the session is still progressing. The terminal wget command currently uses the kernel's dedicated TLS client; user TLS handles and certificate policy should be treated as evolving APIs.

    ABI Rules And Lifecycle

    • Check every return value, especially handle allocation and network operations.
    • Retry SYS_ERR_BUSY and non-blocking SYS_ERR_AGAIN where documented.
    • Close every file, TCP, UDP, and TLS handle before exit.
    • Keep request structures alive until the syscall returns.
    • Keep input/output buffers valid for the entire call.
    • Do not call privileged operations from an ordinary .run process.
    • Use mos_sleep() between polling attempts to yield CPU time.
    • Do not assume kernel structure layouts match SDK structures.

    Conventions and errors

    How SDK calls reach the kernel, what they return, and which calls an ordinary .run program is allowed to make.

    On this pageCalling conventionResult codesPrivilegeWhich headerUnitsMemory

    Calling convention

    Every wrapper ends in one int 0x80:

    RegisterInOut
    raxsyscall number (SYS_*)result
    rdifirst argument
    rsisecond argument
    rdxthird argument

    Calls with more data than three registers (graphics, windows, network, packages, input) pass one pointer to a request structure in rdi. Keep the structure and every buffer it points to alive until the call returns. Versioned structures (syscall_graphics_info_t, syscall_blit_request_t, syscall_input_read_request_t, syscall_window_request_t) must have their size and version fields set and their reserved fields zero; the SDK wrappers do this for you.

    Result codes

    Results come back in rax as a 64-bit value. Failures are small negative numbers, which as unsigned values sit at the very top of the range:

    ConstantValueMeaning
    SYS_SUCCESS0The operation succeeded
    SYS_ERR_GENERIC-1Unspecified failure (out of memory, the driver refused, the file system said no)
    SYS_ERR_BADFD-2Invalid or closed handle; mos_write to an fd other than 1 or 2
    SYS_ERR_NOTFOUND-3Path, window, peer or resource not found, or a connection that has closed
    SYS_ERR_INVAL-4Invalid argument: NULL pointer, out-of-range value, bad structure size or version
    SYS_ERR_PERM-5The calling process may not do this (see privilege)
    SYS_ERR_BUSY-6A shared subsystem (the network stack, a full event queue) is in use: retry
    SYS_ERR_AGAIN-7Non-blocking call with nothing to report yet: call again later

    The constants are defined as ((uint64_t)-N). Compare against them directly, or cast to long and test for a negative value:

    long r = mos_mkdir("0:/data");
if (r == (long)SYS_ERR_INVAL) printf("bad path\n");
else if (r < 0)               printf("mkdir failed: %ld\n", r);

    Some wrappers fold errors into a friendlier value (malloc returns NULL, mos_window_create returns 0, mos_tcp_accept returns 0 for "nobody waiting"); each entry says so.

    Privilege

    .run programs start as PROC_PRIVILEGE_USER processes. Before dispatching, the kernel checks the call against a deny list (syscall_user_may_call() in syscall.c); a denied call returns SYS_ERR_PERM and does nothing.

    Denied to .run programsWhy
    SYS_GRAPHICS drawing primitives (clear, pixel, line, rectangle, circle, triangle, ellipse, text, measure text, set resolution, terminal clear)User programs draw into their own surface and use mos_graphics_blit_surface + mos_graphics_present
    SYS_MANAGER init, update, start, set sample rateThey reconfigure hardware every process shares
    SYS_USB_INIT, SYS_MOUSE_INITThey re-enumerate devices the whole system uses
    SYS_NET_DHCPIt rewrites the address of the shared interface
    SYS_USB_KEY_IS_PRESSED, SYS_MOUSE_GET_STATE, SYS_INPUT_READAllowed only to the process that owns the screen

    Everything else - files, heap, network connections, windows, packages, sysinfo, process list - is open to user programs. The table is not a memory-protection boundary; it closes the specific hole of a program reconfiguring shared hardware through the syscall gate.

    Units

    • Time: milliseconds. mos_uptime() and mos_sleep() both use milliseconds; so do every timeout_ms argument.
    • Colours: window.h and mos_graphics_blit_surface take ARGB8888 pixels, 0xAARRGGBB. Use 0xFF alpha for opaque pixels. The mos_graphics_* primitives take separate r, g, b bytes.
    • IPv4 addresses and ports in net.h are host order: 192.168.1.10 is 0xC0A8010A.
    • Paths are MinimaFS paths such as 0:/programs/app.run. Relative paths are resolved against the terminal's current directory.

    Memory

    There is no libc and no dynamic linker. Everything a program uses is either an inline wrapper from these headers or code compiled into the program. crt0.c supplies _start, runs global constructors (.init_array), calls main(argc, argv) and then mos_exit() with its return value. It also defines out-of-line memcpy, memmove, memset and memcmp, which the compiler may call on its own.

    mos_register_cleanup

    Registers a function the kernel calls when the user presses Ctrl+C in the terminal running this program.

    Files

    MinimaFS file and directory calls. Include minimalos.h.

    Paths look like 0:/etc/System.conf: a drive number, a colon, then an absolute path. A path without a drive prefix is resolved against the terminal's current directory (see mos_getcwd).

    mos_open

    long mos_open(const char* path, long flags);

    Opens an existing file.

    ParameterDescription
    pathFile to open
    flagsSYS_O_RDONLY (0) for read-only; SYS_O_RDWR (or any non-zero value) for read and write

    printf

    long printf(const char* format, ...);

    Formats its arguments and writes the result to stdout.

    ParameterDescription
    formatFormat string
    ...One argument per conversion

    Supported conversions:

    ConversionArgumentOutput
    %d, %iintSigned decimal
    %uunsigned intUnsigned decimal
    %x, %Xunsigned intHexadecimal, lower or upper case
    %ldlongSigned decimal
    %luunsigned longUnsigned decimal

    Windows

    mosWM windows over SYS_WINDOW. Include window.h.

    A window is a kernel-owned ARGB8888 frame buffer plus a title, bounds, flags, a style and an event queue. Your program draws into its own pixel buffer and copies it into the window with mos_window_present; mosWM, the window manager, composites every window onto the screen and turns mouse and keyboard input into window events.

    Windows belong to the process that created them (and its descendants). They are closed automatically when that process exits.

    A minimal window app

    #include "window.h"
#include "stdlib.h"

static int running = 1;
static void on_close(uint32_t id) { (void)id; running = 0; }

int main(void) {
    const uint32_t W = 320, H = 200;
    uint32_t id = mos_window_create(0, 120, 80, W, H, "Hello");
    if (!id) mos_exit(1);
    uint32_t* px = malloc(W * H * 4);

    mos_window_callbacks_t cb = { .onwindowclose = on_close };
    while (running) {
        for (uint32_t i = 0; i < W * H; i++) px[i] = 0xFF2845F5;   /* opaque blue */
        mos_window_present(id, px, W * 4, 0, 0, W, H);
        mos_window_dispatch_events(id, &cb);
        mos_sleep(16);
    }
    mos_window_close(id);
    mos_exit(0);
}

    mos_window_present

    uint64_t mos_window_present(uint32_t id, const uint32_t* pixels, uint32_t pitch,
                            uint32_t x, uint32_t y, uint32_t width, uint32_t height);

    Copies a rectangle of your pixel buffer into the window's frame. mosWM shows the new frame on its next composite.

    ParameterDescription
    idWindow
    pixelsYour buffer, the same size as the window, ARGB8888 (0xAARRGGBB). Use 0xFF alpha
    pitchBytes per row of pixels, at least window width × 4
    x, y, width, heightThe rectangle to copy, in window coordinates. It must lie inside the window

    Returns SYS_SUCCESS, SYS_ERR_INVAL for a rectangle outside the window, a short pitch or a NULL buffer, SYS_ERR_NOTFOUND / SYS_ERR_PERM for a bad window.

    Notes

    • pixels points at the top-left of your whole buffer, not of the rectangle; the kernel offsets into it. Presenting only the part that changed is cheaper than the whole window.
    • After a SYSCALL_WINDOW_EVENT_RESIZED, reallocate the buffer at the new size before presenting again.
    • Each present increments the window's frame_version.

    How it works

    • One object. Every function is called through easyui: easyui.createbutton(...), easyui.setvalue(...). It is a constant structure of function pointers, so it works the same from C and C++.
    • Widgets are ints. Each create... call returns a widget number (1 … 128), or 0 if there was no room. Keep it in an int and pass it to the other calls. Calls with an invalid widget do nothing.
    • Coordinates are pixels inside the window's content area: (0, 0) is the top-left corner below the title bar. Widgets are drawn in the order they were created, so create a panel before the widgets on it.
    • Callbacks take one int, the event's value (see Events). Register them with easyui.recallfunc. Inside a callback, easyui.current says which widget fired, so one function can serve several widgets.
    • The main loop is easyui.run. It handles events, runs timers, redraws only when something changed and sleeps between frames. Callbacks can change any widget; the window is repainted afterwards.
    • Memory. Widgets live in a fixed table (EASYUI_MAX_WIDGETS, 128). Widget text holds up to 127 bytes. List and dropdown items are copied to the heap and freed by clearitems and remove.

    Text

    easyui draws text the way mosWM does:

    • Smooth text (normal). easyui_text.h is a bundled copy of ttrend_outline, the anti-aliased OpenType/TrueType renderer mosWM uses (integer maths only, no libc). When the window opens, easyui loads the Inter fonts mosWM installs, 0:/programs/mosWM/assets/fonts/Inter-Regular.otf and Inter-Medium.otf. Text size 1 is 12 px Inter Regular; size 2 and up is 8 × size px Inter Medium, the same sizes mosWM uses for its own text. Text is proportional: wrapping, alignment and the text-input caret are measured with the real glyph widths.
    • Bitmap fallback. If neither font can be read (mosWM is not installed, or the files are missing), or after easyui.setsmoothtext(0), text uses the 8 × 8 bitmap font mosWM falls back to, scaled by the text size.
    • Your own font. easyui.loadfont loads any .otf or .ttf file instead.

    Run Studio's preview has the same Inter files at the same path, so smooth text looks the same there as on MOSdesk.

    include/easyui_text.h is generated from MOSdesk's mosdesk/libraries/ttrend_outline by tools/bundle-ttrend.py; do not edit it by hand.

    How drawing works

    The kernel keeps a back buffer the size of the screen. A program:

    1. takes ownership of the screen with mos_graphics_acquire;
    2. draws into its own ARGB8888 surface (a malloced uint32_t array);
    3. copies the surface into the back buffer with mos_graphics_blit_surface;
    4. shows the changed rectangle with mos_graphics_present;
    5. gives the screen back with mos_graphics_release, which redraws the terminal.
    #include "graphics.h"
#include "stdlib.h"

int main(void) {
    if (mos_graphics_acquire() != SYS_SUCCESS) { mos_puts("screen busy\n"); return 1; }
    uint32_t w = mos_graphics_get_width(), h = mos_graphics_get_height();
    uint32_t* surf = malloc((size_t)w * h * 4);
    for (uint32_t f = 0; f < 300; f++) {
        for (uint32_t i = 0; i < w * h; i++) surf[i] = 0xFF000000 | ((i + f * 4) & 0xFF);
        mos_graphics_blit_surface(surf, w, h, w * 4, 0, 0, (int32_t)w, (int32_t)h, 0, 0,
                                  SYS_GRAPHICS_BLIT_OPAQUE);
        mos_graphics_present(0, 0, (int32_t)w, (int32_t)h);
        mos_sleep(16);
    }
    mos_graphics_release();
    return 0;
}

    Privilege

    On Minimal-OS a .run program is a user process, and the kernel only lets user processes call these graphics operations: get width, get height, owner, acquire, release, info, blit and present. The drawing primitives - clear, pixel, line, rectangle, circle, triangle, ellipse, text, measure text and set resolution - return SYS_ERR_PERM to a user process; they exist for kernel-privileged callers. Draw shapes and text into your own surface and blit it.

    mos_input_read

    uint64_t mos_input_read(syscall_input_event_t* events, uint32_t capacity,
                        uint32_t timeout_ms, uint64_t* dropped_count);

    ParameterDescription
    eventsArray to fill
    capacitySize of events, 1 … SYSCALL_INPUT_MAX_READ (256)
    timeout_msHow long to wait when the queue is empty, at most 5000. 0 returns at once
    dropped_countIf not NULL, receives the total number of events dropped because the queue was full

    FieldMeaning

    Networking

    IPv4 networking over SYS_NET: interface status, DNS, TCP clients and servers, UDP and the experimental ktls transport. Include net.h.

    Before a program can use the network the interface needs an address. Run dhcp in the terminal first; a .run program cannot do it itself (see mos_net_dhcp).

    Things to know about every call here:

    Functionsmos_net_statusmos_net_is_upmos_net_pollmos_net_resolvemos_net_lookupmos_net_dhcpmos_tcp_connectmos_tcp_sendmos_tcp_send_allmos_tcp_recvmos_tcp_recv_exactmos_tcp_statemos_tcp_closemos_tcp_listenmos_tcp_acceptmos_tcp_unlistenmos_tcp_handoffmos_udp_bindmos_udp_unbindmos_udp_recvmos_udp_recv_timeoutmos_udp_sendmos_tls_connectmos_tls_wait_establishedmos_tls_acceptmos_tls_statemos_tls_sendmos_tls_recvmos_tls_closemos_ip_parsemos_ip_to_stringmos_htonsmos_htonlmos_net_call
    • Host order. IPv4 addresses are uint32_t in host order (192.168.1.10 is 0xC0A8010A), and ports are plain numbers. You only swap bytes for values you put inside your own packets (mos_htons).
    • Polled. The kernel stack only makes progress when a process calls into it. A program that stops calling recv stops receiving. Loop with a short mos_sleep, or use the blocking helpers at the end of this page.
    • One at a time. The stack is not reentrant. A call that finds it in use by another process returns SYS_ERR_BUSY; retry it.
    • Handles. Connections, listeners, UDP bindings and TLS sessions are small positive integers in separate namespaces. They belong to the process that made them; a dead process's handles are closed the next time any process connects, listens or accepts.
    • No driver. With no network card every call except mos_net_status and mos_tcp_state returns SYS_ERR_GENERIC.

    A small HTTP client

    #include "net.h"
#include "stdio.h"

int main(void) {
    if (!mos_net_is_up()) { mos_puts("run dhcp first\n"); return 1; }
    uint32_t ip = mos_net_lookup("example.com", 5000);
    if (!ip) { mos_puts("lookup failed\n"); return 1; }

    long c = mos_tcp_connect(ip, 80, 5000);
    if (c <= 0) { printf("connect failed (%ld)\n", c); return 1; }

    const char* req = "HEAD / HTTP/1.0\r\nHost: example.com\r\n\r\n";
    uint32_t len = 0; while (req[len]) len++;
    mos_tcp_send_all(c, req, len);

    char buf[512];
    long idle = mos_uptime();
    for (;;) {
        long n = mos_tcp_recv(c, buf, sizeof buf - 1);
        if (n < 0) break;                                  /* closed */
        if (n == 0) {
            if (mos_uptime() - idle > 5000) break;
            mos_sleep(5);
            continue;
        }
        buf[n] = '\0'; mos_puts(buf); idle = mos_uptime();
    }
    mos_tcp_close(c);
    return 0;
}

    FarcadeGL (farcadegl.h)

    FarcadeGL is the 3D library of Minimal-OS. It sits on the kernel's FGPU interface (SYS_GPU, described in fgpu_abi.h) and borrows from both OpenGL and Vulkan:

    On this pageHow it runsA first programContextsBuffers and vertex layoutsState and drawingBuilt-in programsShadersTexturesBlendingMathErrors and limitsPerformanceFunction referenceThe FGPU interface underneath
    • Like Vulkan, drawing is recorded into a command buffer and sent to the GPU in one call (fglSubmit / fglPresent). GPU memory is explicit: you create and destroy buffers, textures and shaders.
    • Like OpenGL, state is a handful of simple calls (fglEnable, fglUseShader, fglSetModel ...), matrices are column-major, and shaders are written in a GLSL-style language, FGSL (fgsl.md).

    It is header only: include farcadegl.h and build with ./build.sh.

    How it runs

    The kernel executes command buffers through its FGPU command processor. Today its backend runs on the CPU: vertex stage, clipping, perspective- correct rasterization, depth test, fragment stage, blending. Shaders are compiled in your program to FGPU bytecode, checked by the kernel when you create them, and run per vertex and per pixel by the kernel's shader machine. Surfaces and buffers are placed in the graphics card's video memory when the GPU driver can hand some out (gpu in the terminal shows the VRAM heap).

    Programs do not depend on the backend: when a GPU driver can execute FGPU work on the card itself (see docs/gpu.md in Minimal-OS for the plan for NVIDIA cards), the same programs and the same shader bytecode run there.

    A first program

    #include "farcadegl.h"
#include "window.h"

static const char* vs =
    "uniform mat4 fgl_ModelViewProjection;\n"
    "attribute vec3 position;\n"
    "attribute vec4 color;\n"
    "varying vec4 v_color;\n"
    "void main() {\n"
    "    v_color = color;\n"
    "    gl_Position = fgl_ModelViewProjection * vec4(position, 1.0);\n"
    "}\n";

static const char* fs =
    "uniform float time;\n"
    "varying vec4 v_color;\n"
    "void main() {\n"
    "    float pulse = 0.75 + 0.25 * sin(time * 4.0);\n"
    "    gl_FragColor = vec4(v_color.rgb * pulse, 1.0);\n"
    "}\n";

int main(void) {
    uint32_t win = mos_window_create(0, 100, 100, 640, 480, "Hello 3D");
    FGLContext* gl = fglCreateContext(&(FGLContextDesc){
        .width = 640, .height = 480, .window_id = win, .depth = 1 });

    FGLVertex cube[36];
    fglMakeCube(cube, 1.0f, NULL);
    FGLBuffer vb = fglCreateBuffer(gl, sizeof cube);
    fglBufferData(gl, vb, 0, cube, sizeof cube);

    FGLShader* sh = fglCreateShader(gl, vs, fs);
    if (!sh) { /* fglShaderLog(gl) says why */ return 1; }
    int u_time = fglUniformLocation(sh, "time");

    for (int frame = 0; frame < 600; frame++) {
        fglClearColor(gl, 0.05f, 0.07f, 0.12f);
        fglClear(gl, FGL_COLOR_BUFFER_BIT | FGL_DEPTH_BUFFER_BIT);
        fglEnable(gl, FGL_DEPTH_TEST | FGL_CULL_FACE);
        fglUseShader(gl, sh);
        fglUniform1f(sh, u_time, frame / 60.0f);
        fglSetProjection(gl, fglPerspective(0.9f, 640.0f / 480.0f, 0.1f, 50));
        fglSetView(gl, fglLookAt(fglVec3(0, 1, 4), fglVec3(0, 0, 0), fglVec3(0, 1, 0)));
        fglSetModel(gl, fglRotate(frame * 0.02f, fglVec3(0, 1, 0)));
        fglDraw(gl, vb, 0, 36);
        fglPresent(gl);
    }
    fglDestroyShader(gl, sh);
    fglDestroyContext(gl);
    mos_window_close(win);
    return 0;
}

    Without the shader lines, fglUseProgram(gl, FGL_PROGRAM_PHONG) draws the same cube with the built-in per-pixel lighting.

    Contexts

    typedef struct {
    uint32_t width, height;     // render size
    uint32_t window_id;         // present into this window; 0 = the screen
    int32_t x, y;               // screen position when window_id == 0
    int depth;                  // create a depth buffer
    int page_flip;              // screen only: flip between two VRAM buffers
} FGLContextDesc;

FGLContext* fglCreateContext(const FGLContextDesc* desc);
void fglDestroyContext(FGLContext* gl);

    A context owns the color surface(s) you draw into, an optional depth buffer, and the command buffer being recorded.

    • In a window (MOSdesk): create the window with mos_window_create and pass its id. fglPresent copies each frame into the window.
    • Full screen (terminal): take the screen with mos_graphics_acquire() first. With page_flip set and a GPU that can flip (the QEMU/Bochs adapter can), frames are shown by switching the display to the buffer just drawn instead of copying it.

    Returns NULL when the surfaces cannot be created. fglGetDeviceInfo fills a syscall_gpu_info_t (GPU name, driver, VRAM, backend, caps; caps & FGPU_CAP_SHADERS says shaders are available).

    Buffers and vertex layouts

    FGLBuffer fglCreateBuffer(FGLContext* gl, uint32_t bytes);

    A buffer is up to 16 MiB of GPU memory. Index buffers hold uint32_t indices. Everything a process creates is freed when it exits.

    Vertex buffers hold FGLVertex by default:

    StructFloatsAttributes (location)
    FGLVertex10position xyz (0), normal xyz (1), color rgba (2)
    FGLVertexUV12the same, plus texture coordinates uv (3)

    Call fglVertexLayoutUV(gl) before drawing FGLVertexUV data, and fglVertexLayoutDefault(gl) to go back. For your own vertex struct, describe where each attribute location sits:

    typedef struct { float x, y; float u, v; float shade; } MyVertex;

static const FGLAttribute attrs[] = {
    { offsetof(MyVertex, x), 2 },       // location 0: vec2 (z = 0, w = 1)
    { offsetof(MyVertex, u), 2 },       // location 1
    { offsetof(MyVertex, shade), 1 },   // location 2
};
fglVertexLayout(gl, sizeof(MyVertex), 3, attrs);

    Offsets and the stride are in bytes and must be multiples of 4; a vertex is at most 64 floats; there are 8 locations. Missing components read as (0, 0, 0, 1), so a 2-float position is a point at z = 0. The layout is context state: it applies to every following draw, with shaders and with the built-in programs (which read locations 0, 1 and 2).

    In a shader, attributes get their location from layout(location = N), or from their name: position, normal, color, uv / texcoord (also with a_, in_, a or in prefixes) are 0, 1, 2 and 3. See fgsl.md.

    Shaders

    FGLShader* fglCreateShader(FGLContext* gl, const char* vertex_src, const char* fragment_src);

    fglCreateShader compiles both stages with the FGSL compiler (fglsl.h), links them (varyings and uniforms are matched by name), and loads the program onto the GPU. On failure it returns NULL and fglShaderLog(gl) holds a message such as

    fragment shader line 12: unknown identifier 'normall'

    The language is GLSL ES 1.0 / GLSL 1.30 with a few limits (no structs, no while, loops must have constant bounds); fgsl.md has the full reference. The compiler runs inside your program and takes well under a millisecond for typical shaders; create shaders once at startup, not every frame.

    Textures

    Textures are ARGB8888 (0xAARRGGBB), rows top to bottom, up to 4096 × 4096. In a shader, texture(sampler, uv) returns vec4(r, g, b, a) in 0..1. uv = (0, 0) is the top-left corner of the image and (1, 1) the bottom-right; fglMakeCubeUV maps each face upright.

    Each sampler2D uniform gets a texture unit (0-3, in declaration order). fglUniformTexture(gl, sh, loc, tex, flags) binds a texture to that sampler's unit; fglBindTexture binds to a unit directly. Flags:

    FlagEffect
    FGL_TEXTURE_LINEARBilinear filtering (default: nearest texel).
    FGL_TEXTURE_CLAMPCoordinates outside 0..1 use the edge texels (default: the texture repeats).

    Bindings are context state, like the vertex layout.

    Blending

    fglEnable(gl, FGL_BLEND) mixes each new pixel with what is already there using the fragment's alpha: color = src.rgb * src.a + dst.rgb * (1 - src.a). Draw opaque geometry first, then transparent geometry back to front. With the built-in programs, alpha comes from the vertex color.

    Math

    FGLVec3, FGLMat4 and: fglVec3, fglAdd, fglSub, fglScale3, fglDot, fglCross, fglNormalize, fglIdentity, fglMul, fglTranslate, fglScale, fglRotate(angle, axis), fglPerspective(fovy, aspect, near, far), fglLookAt(eye, center, up), fglNormalMatrix, and fglSin, fglCos, fglTan, fglSqrt (the SDK has no libm).

    fglMakeCube(out, half_size, face_colors) writes the 36 vertices of a cube with one color per face (NULL for the default colors); fglMakeCubeUV does the same with texture coordinates.

    Errors and limits

    • fglPresent/fglSubmit return -1 and set gl->error to the first failed SYS_GPU result (SYS_ERR_INVAL for a bad command, SYS_ERR_NOTFOUND for a destroyed buffer or texture).
    • fglCreateShader returns NULL; see fglShaderLog. If the kernel rejects a program the compiler produced, the reason is written to the serial log (fgpu: shader program rejected: ...).

    Performance

    The CPU backend runs on one core. Measured for the fglcube scene in a 640 × 480 window on a 2.8 GHz Xeon core: about 11 ms per frame with the built-in Phong program and about 42 ms (24 fps) with fglcube --shader (a 60-instruction fragment shader over about 180,000 pixels), so a full shader costs roughly 4 times a built-in program. Fragment shaders run 8 pixels at a time with SSE. Under QEMU without KVM everything is many times slower. Tips:

    • Do per-vertex work in the vertex shader and pass it as a varying; the fragment shader runs for every pixel.
    • Fewer varyings and fewer instructions are faster. discard makes the depth buffer update after the fragment shader instead of before it.
    • Use the built-in programs for objects that need nothing special.

    The FGPU interface underneath

    SYS_GPU (40) takes a syscall_gpu_request_t. Operations: INFO, CREATE_SURFACE, DESTROY_SURFACE, CREATE_BUFFER, UPLOAD_BUFFER, DESTROY_BUFFER, SUBMIT, READBACK, PRESENT, RELEASE_DISPLAY, and (ABI version 2) CREATE_PROGRAM, DESTROY_PROGRAM, WRITE_SURFACE.

    A command buffer is a list of 32-bit words; each command starts with FGPU_CMD(opcode, length_in_words): BIND_TARGET, VIEWPORT, CLEAR, SET_STATE, SET_PROGRAM, SET_UNIFORMS, DRAW, and (version 2) SET_SHADER, SET_CONSTANTS, SET_VERTEX_LAYOUT, BIND_TEXTURE. Every submit starts from default state.

    A shader program is a blob of FGPU bytecode: a header, the vertex and fragment instructions (five words each: opcode, destination, three sources, with swizzles and negate/abs modifiers on vec4 registers) and a constant pool. The instruction set and register files are described at the end of fgpu_abi.h. Jumps only go forward, so every program finishes; the kernel checks every instruction when the program is created. You can produce blobs yourself, but fglsl_compile (fglsl.h) is the supported way.

    A shader is a list of global declarations and functions, with one void main(). Both GLSL styles work:

    Statements

    • Assignment =, +=, -=, *=, /=, and ++ / -- (as statements).
    • if (...) ... else ...
    • for (int i = A; i < B; i++) ... — the start, end and step must be constants (<, <=, >, >=, !=; i++, i--, ++i, i += n, i -= n). Loops are unrolled, at most 256 times. break and continue work. Inside the loop, i is a constant, so it can index arrays.
    • discard; (fragment shader) drops the pixel.
    • return; / return expr;
    • while and do loops are not supported (every program must finish in a known number of steps).

    Expressions

    Operators, from lowest to highest precedence: ?:, ||, &&, == !=, < > <= >=, + -, * /, unary - + !, then calls, [] and swizzles. Arithmetic works component by component; a float mixes with any vector (v * 2.0). mat4 * vec4, vec4 * mat4 and mat4 * mat4 are matrix products. Comparisons and &&, ||, ! work on scalars and give 0.0 or 1.0.

    Functions

    User functions are supported and inlined at each call: parameters are copies (in); out / inout parameters and recursion are not supported. A function must be declared before main is compiled, in any order.

    3D library · C · header only

    FarcadeGL

    The 3D library of Minimal-OS. Drawing is recorded into a command buffer and submitted in one call, like Vulkan; state is a handful of simple calls and matrices are column-major, like OpenGL. Shaders are written in FGSL, a GLSL-style language compiled inside your program.

    FarcadeGL referenceFGSL languageHow the GPU side works

    How it runs

    FarcadeGL sits on the kernel's FGPU interface, SYS_GPU. The kernel checks every command buffer and runs it through its 3D pipeline: vertex stage, clipping, perspective-correct rasterization, depth test, fragment stage and blending. Shaders become FGPU bytecode in your program; the kernel verifies the bytecode before running it per vertex and per pixel. Surfaces and buffers go into video memory when the GPU driver can hand some out.

    Today the pipeline runs on the CPU. Programs do not depend on that: when a driver can run FGPU work on the card itself, the same programs and the same bytecode run there.

int main(void) {
    uint32_t id = mos_window_create(0, 80, 64, 640, 360, "Example");
    uint32_t* pixels = calloc(640 * 360, sizeof(uint32_t));
    for (;;) {
        syscall_window_event_t ev;
        while (mos_window_next_event(id, &ev) == SYS_SUCCESS)
            if (ev.type == SYSCALL_WINDOW_EVENT_CLOSE_REQUEST) { mos_window_close(id); return 0; }
        /* draw ARGB8888 pixels, then */
        mos_window_present(id, pixels, 640 * 4, 0, 0, 640, 360);
        mos_sleep(16);
    }
}

    Events cover resize, close requests, minimise, maximise, focus, keys (USB HID codes), mouse and wheel. mos_window_dispatch_events maps the window events to callbacks, and mos_window_set_style, mos_window_set_resizable and mos_window_set_fullscreen change how a window behaves.

    Security model

    Applications render into their own buffer; the kernel copies those pixels into the window surface, so no app ever holds another app's surface. Only a window's owner (or the process that launched it) can change it, and only the focused window's owner may change the pointer. The window-server role is granted only to the installed mosWM.run launched by the OS, and only after it owns the framebuffer.

    The compiler

    Studio includes mcc, a C11 and C++ compiler written for it. C++ is lowered to the same syntax tree as C — methods take an explicit this, constructors and destructors become calls at the right places, virtual calls go through a vtable, templates are instantiated per use — so both back ends handle it unchanged. It preprocesses and type-checks your code against the real SDK headers (only the three inline-assembly syscall stubs are swapped for a __syscall builtin) and has two back ends:

    • Preview: JavaScript that runs in a Web Worker against an emulated memory with the same LP64 layout as the device. Every syscall goes to a small emulation of the Minimal-OS kernel that reads the same request structures the real kernel does.
    • Build: x86_64 machine code, linked into a position-independent ELF at base 0 with only R_X86_64_RELATIVE relocations, packed as MINIRUN1, optionally wrapped in an MPKG0001 package.

    Both back ends are checked against GCC and G++ on the same test programs, which print identical output — for C++ that includes the exact order of constructor, copy and destructor calls.

    The preview

    The preview recreates mosWM: window chrome with the kernel's default style or your own, moving, resizing, edge tiling, minimise and maximise, a taskbar, and a terminal for programs that print. Mouse and keyboard input arrive as the same window events mosWM posts, with USB HID key codes. Programs that use graphics.h draw to a full-screen framebuffer with the kernel's 8×8 font.

    3D works too. FarcadeGL programs draw through a JavaScript port of the kernel's GPU pipeline, with the same lighting, texturing, wireframe and FGSL shaders. Its frames are checked against the kernel's own rasterizer and match it pixel for pixel, apart from a few edge pixels. Try the 3D cube sample.

    Limits

    • No goto, bit-fields, variable-length arrays, inline assembly or statement expressions; long double is double.
    • C++ without exceptions or RTTI (like the SDK), lambdas, rvalue references, multiple inheritance, member templates or class template specialization.
    • The preview has no network card and cannot run SYS_EXEC or SYS_PKG. Its GPU cannot page flip, so full-screen FarcadeGL programs present by copying.
